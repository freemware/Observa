# Current Project

## What we are building

WebLens is a Chrome/Brave browser extension that visually explains the privacy and tracking activity occurring while a user browses a website.

Instead of presenting raw developer logs, WebLens transforms observable browser activity into an interactive map showing third-party connections, cookies, trackers, analytics services, and advertising systems.

The question it answers: **what is this website doing behind the scenes, and where is my data potentially going?** As of M6, it can also answer: **if I block this, what actually changes — and did anything break?** As of v0.11.0, it can also answer: **in what order did my browser talk to these domains, and did anything on this page send data that looks personal or trackable?** As of v0.12.0/v0.12.1, it can also answer: **specifically what category of personal info (email, location, tracking ID...) is a given domain or cookie collecting — and, on request, the exact value.**

## Core product experience

1. Visit a website.
2. Open WebLens.
3. Start or view the current analysis session.
4. See what domains the website communicates with.
5. Identify first-party and third-party connections.
6. Identify known trackers, analytics platforms, and advertising services.
7. Inspect cookies created by the website.
8. Understand why each detected service matters.
9. Explore the activity visually instead of reading raw network logs.
10. Optionally block a specific tracker on this one site, reload, and see a before/after receipt of what changed.
11. Replay the session's requests in the order they happened (v0.11.0 — "Data Journey").
12. See when a request appears to send something that looks like personal information or a tracking identifier, redacted (v0.11.0 — "Data Exposure Detector").
13. See at a glance, on the graph/table, which domains and cookies show a personal-data or tracking-ID match — and, on request, reveal the exact matched value (v0.12.0 badges + v0.12.1 cookie-value scanning/reveal toggle).

## Architecture (current)

This is the established architecture referenced by CLAUDE.md Rule 4. Changing any of it requires approval.

**Everything runs locally. No backend, no server.** As of v0.11.0 there is exactly one deliberate exception, described under "Tracker/cookie list refresh" below — everything else remains observe-only with zero network egress from WebLens itself.

**Data flow:** `webRequest` events -> normalize (+ exposure detection) -> in-memory buffer -> coalesced flush to `chrome.storage.session` -> UI reads from storage.

One additional, **opt-in, off-by-default** data flow exists alongside the per-tab session flow:

- **Session history** (`history.js`): when enabled via the dashboard settings panel, `session.js` writes one summarized record per site per calendar day (counts only — third-party count, cookie count, tracker-match count) to `chrome.storage.local` when a session ends. No raw requests, no URLs, no cookie names are retained — summary counts only.

This store is capped in size (oldest entries evicted), described to the user in the dashboard settings panel, and wiped by a "Clear history data" control that leaves the existing per-tab session data untouched (that has its own clear control). As of v0.10.0, the Organizations tab also surfaces this history as a plain-English diff ("This site added 2 trackers since Tuesday") rather than only a day-by-day bar chart — see "Design system" below.

A second flow exists as of v0.11.0 — see "Tracker/cookie list refresh" below. It is the one place WebLens's own code initiates a network request rather than only observing requests the visited site makes. It shipped opt-in/off by default in v0.11.0 and switched to on-by-default in v0.11.2 (still user-toggleable).

**"Companion web dashboard" is an extension-hosted page**, not a hosted website. It runs on the `chrome-extension://` origin and reads local storage directly. A hosted dashboard would require transmitting browsing telemetry off-device and is explicitly out of scope. (See Open decisions.)

**Session model:** one session per tab, keyed by tab ID, started at top-level navigation commit and ended at the next top-level navigation or tab close. Per-tab session data does not survive browser restart by default — this is unchanged. Session history summaries are the only passive data that intentionally survives a restart, and only when the user has opted in.

**First-party vs third-party** is determined by eTLD+1 comparison using a bundled public suffix list, not naive domain string matching. As of v0.11.1, IP-address hostnames (IPv4 and IPv6) are recognized and returned as-is rather than being sliced like a domain — see "v0.11.1" below for why this mattered.

**Bubble map grouping:** the dashboard's graph groups nodes by owning organization when one is known (via tracker-list classification), falling back to eTLD+1 when the organization is unclassified. This prevents one company's multiple domains (e.g. `doubleclick.net`, `google-analytics.com`, `googletagmanager.com`) from rendering as separate bubbles. The Table view (v0.11.1) reuses this exact same grouping — a domain's requests were previously listed one row per raw request.

### Data Journey replay (v0.11.0)

A "Replay" button in the dashboard's hero line opens an overlay that plays back the current session's requests in the order the browser actually made them — a chronological list of first-contact events per third-party domain, each annotated with how long after the page started it happened, ending in a one-sentence summary ("Within 1.7s of opening this page, your browser contacted 4 external domains through 9 requests."). No new data is captured or stored — it is built entirely from `request.timestamp`, which WebLens already recorded for every request. Playback timing on screen is scaled/capped for a legible animation; the relative order and the stated real durations are never altered. Provenance: Observed.

### Data Exposure Detector (v0.11.0, extended v0.12.0/v0.12.1)

`classify/exposure.js` runs against every captured request's URL and POST body, looking for parameter patterns that commonly carry personal or tracking information: email addresses, phone numbers, ZIP/postal codes, latitude/longitude pairs (by named parameter, not raw regex on the whole body), and known tracking-ID parameters (`fbclid`, `gclid`, and similar, with a human label per known ID). Low-sensitivity values (UTM campaign params, the page URL itself) are shown verbatim since they carry no personal content. Findings surface in three places: a dashboard-wide "Notable Finding" when any domain in the session shows exposure, a per-domain "Data leaving the page" section in each domain's detail panel, and (v0.12.0) an at-a-glance marker on that domain's graph node/table row. Provenance: Observed for the fact a pattern-matching parameter was present in the request; WebLens explicitly does not claim the value is accurate, real, or actually the visitor's own data — only that the request contained something matching the pattern.

**Redact-by-default, reveal-on-demand (v0.12.0/v0.12.1 — requested directly).** Through v0.11.0, a match was *always* redacted and the raw value never survived past the detector. Requested directly during v0.12.x's UI work — "if it collects my email... either show me the exact email its collecting, or tell me that its collecting my email" — every finding now carries both a `redacted` preview (still what's shown, and stored/logged, by default — e.g. `j***@example.com`, `941**`) and `raw` (the exact matched substring, e.g. `janedoe@example.com` — never the whole request/cookie, just that one narrow match). The UI shows `redacted` by default and swaps in `raw` only when the user explicitly clicks a per-finding "Show" button, which flips to "Hide" and swaps back. This is a deliberate, requested exception to the pre-v0.12.0 "always redact" rule, scoped narrowly: CLAUDE.md Rule 2's "never write cookie values or full URLs with query strings to **logs**" is about logs specifically, not UI display, so this stays compliant — nothing in the reveal path writes to `console.*` or any durable store; it only ever changes what's rendered in the open detail panel, in response to a click. `raw` values still never leave the tab-scoped `chrome.storage.session` object they already lived in as part of the request/cookie record (see "Data retention" below).

Reading POST body content (`requestBody`) needed no new manifest permission — it's part of the existing `webRequest` grant, just a deeper level of inspection WebLens didn't previously use. Bodies are decoded in-memory only long enough to run the local pattern detectors and are never stored raw (only the redacted preview and the narrow matched substring are).

**Cookie-value scanning (v0.12.0, "Value match" flag + reveal — requested directly).** Previously `cookies.js` discarded `chrome.cookies.getAll()`'s `value` field entirely, and stated so explicitly ("Never reads, stores, logs, or transmits cookie values"). That claim is now narrower, not gone: `getCookiesForUrl()` reads `c.value` transiently, only to run it through the new exported `detectValueExposure(name, value)` (in `classify/exposure.js` — reuses the same `scanEntries()` the request path uses, filtering out the `page`/`campaign` types since those aren't meaningful for a cookie's own value), and attaches whatever it finds as an `exposures` array on the returned `CookieMeta` object. The cookie's actual full value is still never included in that object, returned, stored, or logged — only the detector's output survives (a redacted preview plus, per the reveal-on-demand design above, the narrow matched substring). A cookie with a hit gets a small "Value match" flag next to its name, and its expanded detail gains a "This cookie's value appears to contain:" section reusing the exact same finding-row rendering (and reveal toggle) as request-based findings. `detectValueExposure()` also tries a `decodeURIComponent()` fallback when the direct match against the raw stored value fails — `chrome.cookies.getAll()` returns a cookie's value exactly as stored on the wire, not URL-decoded the way query-string params already are by the time `scanEntries()` sees them, and a percent-encoded cookie value (e.g. `session=user%40example.com`, a common real-world shape) would otherwise be silently missed. This was found and fixed during testing, not assumed up front.

**Combined exposure surfacing (v0.12.0).** The at-a-glance graph/table markers and the session-wide Notable Finding now combine request-sourced and cookie-sourced findings for a domain (`combinedExposuresForEntry()` in `dashboard.js`), so a domain flagged only because of a cookie's value — not anything in its requests — still shows up in both places, not just inside that one cookie's own expanded detail.

**Device/browser disclosure (v0.12.0).** Both the per-domain exposure section and the Insights overlay's Findings intro now include one factual sentence: the browser sends basic device/browser/OS-class info (User-Agent) to every domain automatically as part of standard HTTP — not a WebLens detection, just how requests work, included so "what does this collect about my device" has a truthful answer even though WebLens does not do device fingerprinting (that remains out of scope pending the deferred `scripting`-permission feature — see Open Decisions #7).

**MV3 CSP and inline onclick — a real bug found and fixed in v0.12.1.** While testing the new reveal/hide toggle, clicking "Show" silently did nothing. Root cause, confirmed directly (Chrome logged `Refused to execute inline event handler ... script-src 'self'` to the console): MV3's default extension-page CSP (`script-src 'self'`, no `unsafe-inline`) blocks every inline `onclick="..."` attribute outright, with no exception for handlers that only touch `this`/sibling nodes. This wasn't unique to the new reveal button — three *pre-existing* interactive elements in `dashboard.js` (`.dsec-hd` section-collapse headers, `.ck-item` cookie rows, `.req-item` request rows) used the same inline-onclick pattern and were, on inspection, equally broken; nothing had ever verified those toggles actually opened/closed anything, only that clicking them didn't throw an error. All four were fixed the same way, matching a delegation pattern the file already used correctly elsewhere (the org-card and M6 verify-button toggles): a single `click` listener on `#detail` (and one on `#story-body` for the Insights overlay's own section headers) that dispatches on `event.target.closest(...)`, since `#detail`'s content is regenerated on every node selection anyway. Regression-covered: `test/new-features-verify.js` now clicks the actual "Show"/"Hide" button and asserts the visible text changes (not just that the DOM carries the data), and confirms revealing a finding doesn't also toggle its parent section closed; `test/cookie-value-exposure-verify.js` (new) exercises the same accordion-open/reveal-toggle interactions specifically for a cookie's own expanded body. This is the kind of thing CLAUDE.md Rule 7 exists for — the code looked correct and had shipped once already (v0.12.0's badges) before this was caught by actually clicking the button in a real loaded extension, not by reading the diff.

### Tracker/cookie list refresh (v0.11.0)

The bundled Disconnect Tracking Protection list and Open Cookie Database (see "Tracker data source" in Open decisions) are dated snapshots that go stale over time. `background/list-refresh.js` adds a mechanism (a checkbox in dashboard settings, **on by default since v0.11.2**; shipped opt-in/off in v0.11.0) that re-fetches the same two public sources the bundled snapshots were generated from, about once a day (`chrome.alarms`, new `alarms` permission), parses them into the exact shape `classify/tracker-list.js` and `classify/cookie-db.js` already use, sanity-checks the result against a size floor (rejects a parse that looks corrupted or schema-changed rather than silently overlaying broken data), and stores it in `chrome.storage.local` as a live overlay. `tracker-list.js`/`cookie-db.js` check the live overlay first and fall back to the bundled snapshot — so a refresh that's disabled, never run, or fails always degrades to exactly the pre-v0.11.0 behavior, never to missing or broken classification. A "Revert to bundled snapshot" control clears the overlay.

**This is the one place WebLens makes a network request of its own** — every other request the extension observes is triggered by the site being visited, not by WebLens. It fetches only two fixed, publicly documented URLs (the same sources the bundled data already cites) and sends nothing — no browsing data, no telemetry, no user identifier. This required explicit sign-off before building since it is the project's first outbound request of any kind (Rule 4); it was scoped deliberately narrowly (fixed URLs only, opt-in, fails safe) to preserve the "no backend, no server" principle in spirit even though it is, technically, WebLens-initiated egress.

**Resolved in v0.11.2:** the daily refresh is now on by default (still user-toggleable off in settings) — see "v0.11.2" below. **Still open:** whether to broaden beyond Disconnect to a second tracker-intelligence source (e.g. DuckDuckGo Tracker Radar or EasyPrivacy — both already named as candidates in REFERENCES.md), or shorten the refresh interval below once a day. See Open decisions below for the sizing/licensing breakdown of each.

Found via a new end-to-end test of the block/unblock flow (see "Testing coverage added" below) — that workflow had no prior automated coverage at all, on any page. Fixed by detecting IPv4/IPv6 hostnames and returning them unchanged; regression-covered by a new unit test (`test/classify-unit.mjs`).
- **Testing coverage added, closing two real gaps identified while auditing existing tests:** (1) the M6 Verify & Protect block/unblock workflow — declarativeNetRequest rule creation, the before/after "privacy receipt" overlay, and unblocking — had no automated test anywhere before this phase; it's now covered end-to-end in `test/gaps-and-branding-verify.js` (which is also what caught the eTLD+1 bug above). (2) The popup previously only had cosmetic test coverage (icons render, theme toggles); the same file adds a basic functional smoke check that the popup actually renders session data. Note: that popup check currently shows 0/0 counts under Playwright specifically because opening the popup via `page.goto()` (rather than a real toolbar-icon click) makes the popup's own tab the "active tab" it queries against, not the page tab with the test traffic — a test-harness limitation consistent with the `about:blank`-navigation caveat already documented under "Known testing limitations," not a product bug.

### Design system (v0.10.0) — popup/dashboard visual consolidation

Before v0.10.0 the popup and dashboard were visually two different products (dark-only popup with a hardcoded `#07090f` background vs. a light-only dashboard), used emoji (🚫🛡📖⚠️⚙) for structural chrome, and split six related views (Graph, Table, Trend, Story, Findings, Protect) across the dashboard topbar. v0.10.0 is a design pass, not a feature or architecture change — no new permissions, no new data collected.

- **Shared theme tokens** (`ui/theme.css`): one set of CSS custom properties (background/surface/border/text/accent/shadow/radius, plus semantic RGB-triple colors like `--danger-rgb` so callers pick their own opacity) consumed by both `popup.html` and `dashboard.html`. Dark is the default; `@media (prefers-color-scheme: light)` follows the OS, and an explicit `data-theme="light"|"dark"` attribute on `<html>` always overrides it. The three-state preference (system/light/dark) is stored via `settings.js`'s `theme` field (`chrome.storage.local`, the existing `storage` permission — no new grant) and applied at bootstrap by `ui/theme.js`. A theme toggle button (cycles system → light → dark) lives in both the popup header and the dashboard topbar.

Replaces emoji in structural chrome (nav, buttons, category badges, status indicators) in both popup and dashboard. Emoji were deliberately kept in two places: mid-sentence narrative content (Story Mode's prose, e.g. "⚠️ 2 fingerprinters detected") and the Protect panel's tool/brand recommendation icons (🧱🦁📦🧹🌐) — these read as informal content glyphs rather than product chrome, and converting them added visual noise without improving legibility.

Table view is now a mode toggle on the Graph view (`.mode-btn[data-mode="map"|"table"]`) instead of a separate tab. Trend moved inside the Organizations tab (`#trend-inner`, nested in `#orgs-view`). Story + Findings + Protect merged into a single "Insights" overlay with all three as collapsible sections (reusing the existing accordion helper), opened by one topbar button instead of three.
- **Hero line:** the graph view now leads with one plain-English sentence by default ("*hostname* contacted 12 domains, 3 of them trackers"), generated from the same domain-map data the bubble map already builds, with the bubble map underneath as the "explore further" layer — replacing a stat-grid-first layout. (v0.11.1 made this unambiguously the *one* primary summary line by de-emphasizing the topbar stat strip that used to duplicate it — see "v0.11.1" above.)
- **Skeleton loading:** the popup's `—` placeholders (summary strip counts, domain/cookie lists) are replaced by a shared shimmer utility (`.skel` in `theme.css`) while the popup's first message round-trip to the service worker is in flight, so the popup reads as loading rather than broken on open.

(The logo gradient was actually missed by this audit — a leftover hardcoded gradient was found and fixed in v0.11.1, see above.)
- **"What changed since last visit"** (Organizations tab, uses the existing opt-in `history.js` store, no schema change): a pure function (`buildTrendDiff()` in `dashboard.js`) diffs the two most recent recorded days for the current site and renders a sentence like "This site added 2 trackers, added 1 cookie since Tuesday" (or a "no change" / all-decreased state with a different tone/icon). Recent dates render as a weekday name ("since Tuesday"); older ones fall back to a month/day date. Verified with a standalone unit test (`test/trend-diff-unit.js`) exercising the date math and delta wording directly against the shipped function, since end-to-end browser testing of this path hits an unrelated Playwright-only artifact (see "Known testing limitations" below).
- **Known testing limitations:** Playwright's `context.newPage()` + `page.goto()` commits an `about:blank` navigation before the real URL. This is harmless in itself — WebLens correctly overwrites that tab's session with the real `pageUrl` once the real navigation commits (`startSession()` in `session.js` replaces the whole session object, it doesn't merge). What actually caused flaky E2E runs, root-caused during v0.11.0 testing, was two separate real issues, both now fixed: (1) `session.js`'s persisted tab index (`sessions:index` in `chrome.storage.session`) did a non-atomic read-modify-write, so two tabs committing navigations close together could race and one tab's entry would silently vanish from `weblens:getSessions` — fixed with an in-process write queue (`_updateIndex`, now serialized). (2) On a freshly launched browser profile, a fast local navigation can commit before the service worker's own `webNavigation` listener has finished registering (its module graph — several imported files — is still loading), and Chrome does not replay missed events to a late listener, so that tab's first navigation was silently never captured. This is a real, if narrow, MV3 cold-start race, not a Playwright artifact; the E2E test files work around it by confirming a live message round-trip to the service worker (proving its listeners are registered) before navigating any tracked tab. A production user reloading the page after installing/enabling the extension is not affected in practice, since by then the service worker has been running for a while, but this is worth keeping in mind if a "capture missed on first-ever load" report ever surfaces. As of v0.11.1, opening the popup directly via `page.goto()` (rather than a real toolbar click) is a separate, additional testing-only limitation — see "v0.11.1" above. As of v0.12.1, a related but distinct class of bug was found this same way: MV3's page CSP silently blocks inline `onclick` attributes entirely (no console *error*, just a logged CSP-violation warning easy to miss) — see "MV3 CSP and inline onclick" under "Data Exposure Detector" above. Any future interactive HTML generated as a template string in `dashboard.js` must use delegated `addEventListener` dispatch, never an inline `onclick="..."` attribute, even for a handler that looks self-contained. As of v0.12.2/v0.12.3, popup-only rendering logic (e.g. the partial-block count display) is tested deterministically by stubbing `chrome.tabs.query`/`chrome.runtime.sendMessage` at the message-passing boundary via `page.addInitScript()` rather than relying on real network traffic or real tab-focus state — see `test/popup-blocked-pill-verify.js`.

### Verified platform facts

- MV3 removed `webRequestBlocking` for non-policy-installed extensions, but the observational `webRequest` API is otherwise unchanged and available. WebLens only observes via `webRequest`, so this is sufficient. (Chrome extensions webRequest reference.)
- `declarativeNetRequest` is MV3's blocking mechanism and remains available to normal extensions; WebLens uses it only for explicit, user-initiated, site-scoped blocks (M6), never proactively.
- The service worker terminates after ~30 seconds of inactivity and loses all global state. (Chrome service worker lifecycle documentation.)
- `chrome.cookies` can read `HttpOnly` cookies, which page JavaScript cannot. This is a real capability and a real responsibility — metadata only (as of v0.12.0, plus a transient value read purely to run the local pattern detector — see "Cookie-value scanning" above).
- `chrome.webRequest.onErrorOccurred`'s `details.error` reports Chrome's net-error string (e.g. `net::ERR_BLOCKED_BY_CLIENT`) for the request that just failed/was cancelled — this is what lets WebLens tell "blocked by an extension's rule" apart from a genuine network failure. Confirmed via a live `declarativeNetRequest` rule + Playwright test (now a full end-to-end block/unblock test as of v0.11.1, not just the net-error signal in isolation).
- `webRequest.onBeforeRequest`'s `requestBody` extra-info option requires no new manifest permission — it's covered by the existing `webRequest` grant — but does expose POST body content (form fields or raw bytes) that WebLens did not previously inspect. Confirmed via the shipped Data Exposure Detector (v0.11.0).
- `chrome.alarms` requires its own manifest permission (`alarms`) and is the standard MV3-safe way to schedule recurring background work without an always-running timer, since the service worker itself is not long-lived. Confirmed via the shipped list-refresh mechanism (v0.11.0).
- `declarativeNetRequest`'s `initiatorDomains` condition matches literally against the site's eTLD+1 string — it has no awareness that an IP address isn't a domain name. Getting eTLD+1 derivation wrong for an IP-hosted page (see "v0.11.1" above) silently misfiles the rule; Chrome doesn't error, the rule is just scoped to a key that never matches real traffic.
- **MV3's default extension-page CSP (`script-src 'self'`) blocks inline event-handler attributes (`onclick="..."` etc.) unconditionally** — there is no exception for a handler that only manipulates `this`/sibling DOM nodes with no external reference. Chrome reports this as a console warning ("Refused to execute inline event handler..."), not a thrown JS error, so a broken inline handler can ship and pass casual testing (no crash, no red error) while silently doing nothing on click. Confirmed directly in v0.12.1 (see "MV3 CSP and inline onclick" above) after three pre-existing inline-onclick toggles turned out to have never actually worked. `chrome.cookies.getAll()` also returns a cookie's value exactly as stored, not URL-decoded — a percent-encoded value needs its own `decodeURIComponent()` pass to pattern-match correctly, unlike query-string params which arrive already decoded via `URLSearchParams`.

### Permission budget

Every permission requires a justification. Current set:

| Permission | Justification |
|---|---|
| `webRequest` | Observe outbound requests, including (v0.11.0) POST body content for the Data Exposure Detector. Core capability; no alternative. |
| `webNavigation` | Detect top-level navigation commit to start/end a per-tab session at the right time. |
| `cookies` | Read cookie metadata for the active site — as of v0.12.0, this includes a transient read of each cookie's value to run it through the same local pattern detector requests already go through (see "Cookie-value scanning" above); the value itself is still never returned, stored, or logged. |
| `storage` | Persist session state across service worker termination, plus (opt-in) session history and (on by default since v0.11.2, user-toggleable) the live tracker/cookie list overlay. Also holds the cosmetic `theme` preference (v0.10.0) — no new grant. |
| `tabs` | Associate requests with the originating tab and session; reload the tab as part of the M6 verify workflow. |
| `publicSuffix` | Accurate eTLD+1 derivation via the browser's built-in Public Suffix List, falling back to a bundled hand-rolled list (whose IP-address handling was fixed in v0.11.1). |
| `declarativeNetRequest` | M6 — block a specific tracker on the current site only, and only in direct response to the user clicking "Block" in the dashboard or popup. Never used proactively or based on classification alone. |
| `alarms` | (v0.11.0) Schedule the once-a-day tracker/cookie list refresh without an always-running timer. On by default since v0.11.2; only fires if the setting is enabled (user can turn it off). |
| `<all_urls>` host permission | Required for webRequest/cookies to see arbitrary sites, and (v0.11.0) already covers the two fixed URLs the list-refresh `fetch()` calls — no separate host permission was needed for that. |

`<all_urls>` is the opposite of minimal and is the single largest privacy-surface decision in the project. It is accepted only because per-site activation would prevent capture of the page load itself. Revisit if `activeTab` proves sufficient.

Session history introduces no new permission — it uses `chrome.storage.local`, already covered by the existing `storage` permission. What changes is not *what WebLens can access* but *how long it remembers what it observes*, which is why it is opt-in and off by default rather than being covered by the existing permission grant alone.

Not requested: `history`, `downloads`, `debugger`, `management`, `identity`, `webRequestBlocking`, `scripting`/content scripts.

## Summarization rule

The product must be understandable in ~10 seconds without inventing a privacy score.

Permitted summary: counts by category, named owning organizations, first vs third-party split, cookie counts by attribute.

Not permitted: a 0–100 rating, letter grade, "risk level" as a composite page-level score, or any composite number implying measured severity. Per-finding severity labels (high/medium/low on an individual finding, not a whole-page score) are treated as acceptable under this rule since they don't produce a composite rating — this distinction was raised for the M4 Notable Findings engine and is recorded here as the resolution. The M6 breakage caveat follows the same discipline: a worded flag, never a score, never a "safe/unsafe" verdict. The v0.11.0 Data Exposure Detector follows it too: findings get a severity label (high when personal-info patterns are involved, medium for tracking-ID-only), never a composite exposure score.

## Data retention

Two tiers exist, and the UI must make the distinction visible rather than presenting them as one undifferentiated "your data" bucket:

1. **Per-tab session data** (unchanged). Lives in `chrome.storage.session`. Cleared automatically on browser restart. User-clearable via the existing per-tab clear control. As of v0.11.0, a request's `exposures` field lives here too — same lifecycle as the rest of the request; as of v0.12.0, a cookie's `exposures` field does too (attached at read time by `cookies.js`, not persisted separately — cookies themselves are re-read from `chrome.cookies` on each dashboard load, not cached by WebLens). As of v0.12.1, an `exposures` entry carries both `redacted` and `raw` (the narrow matched substring, never the whole request/cookie value) — see "Data Exposure Detector" above for why storing `raw` here is compliant with Rule 2, which restricts writing to logs, not this in-memory/session-scoped object the UI already reads from.
2. **Opt-in durable data** (session history only, M5). Lives in `chrome.storage.local`. Off by default — the user must explicitly enable it in the dashboard settings panel, where the panel states in plain language what is stored (counts only; never URLs, never cookie names or values, never full request lists) and for how long (age-capped at 30 days/site, oldest evicted first). Cleared via its own "Clear history data" control.

M6's block list is a third, distinct category: not opt-in/off-by-default data collection, but a durable *action* record (which domains are blocked, where) that exists only because the user explicitly created each entry by clicking "Block." It has its own "Remove all blocks" control in settings, separate from history's clear control, since clearing it has a real effect (unblocks everything) rather than just deleting records.

The v0.11.0 tracker/cookie list overlay is a fourth category: not data *about the user or their browsing* at all — it's a cache of public, non-personal reference data (which domains are trackers, which cookies mean what) fetched from two fixed URLs. It's opt-in, has its own "Revert to bundled snapshot" control, and is documented here because it's the one durable store populated by a WebLens-initiated network request rather than by observing the user's own browsing.

Any future durable storage beyond these follows the same rule: user-visible, off by default unless there's a strong reason otherwise, and clearly clearable.

## Known accuracy limitation: Brave

Brave Shields blocks many requests before an extension observes them. The same page will produce materially different results in Chrome and Brave. This is not a bug — it is a visibility limit, and under CLAUDE.md Rule 3 it must be disclosed in the UI rather than silently producing a quieter graph.

Similarly, WebLens cannot see: requests made before the extension's listeners are registered, activity in other browser profiles, server-side data sharing that occurs after a request arrives, or (M6) whether a page visually or functionally broke after a block — only a soft proxy signal (first-party request completion) is available, and it is presented as a caveat, not a verdict. The v0.11.0 Data Exposure Detector has the same category of limit: it can only see patterns in the request WebLens observes (URL + POST body) or, as of v0.12.0, a cookie's stored value — not encrypted payloads, not values sent via other channels (WebSocket frames, `sendBeacon` binary payloads, etc.), and a pattern match is not proof the value is real or belongs to the visitor — only that something matching the pattern was present in that request/cookie. It also cannot see genuine device/hardware signals (screen size, GPU, installed fonts, etc.) — the User-Agent disclosure sentence added in v0.12.0 is a factual note about standard HTTP behavior, not a WebLens-performed detection.

## What to avoid

Do not: build a platform before the extension works; claim visibility WebLens does not have; label every third-party service as malicious; treat every cookie as dangerous; confuse privacy risk with security vulnerability; transmit telemetry externally; expose a cookie value or full URL to **logs** (as opposed to the UI's own redact-by-default/reveal-on-demand display, added in v0.12.1 — see "Data Exposure Detector" above for the distinction and why it's compliant with Rule 2); create arbitrary privacy scores; use AI as the primary detection engine; overwhelm users with raw requests; request excessive permissions; introduce cloud infrastructure prematurely; build features outside the current milestone; make durable data collection the default without explicit opt-in; block anything the user did not explicitly ask to block; or claim WebLens can detect that a site "broke" — only that a weak proxy signal moved.

## Open decisions

1. **Extension-hosted dashboard confirmed?** Written above as a local extension page. Confirmed — no change.
2. **Tracker data source and bundling strategy — refresh cadence/default resolved (v0.11.0 mechanism, v0.11.2 default), broadening still open.** Disconnect Tracking Protection list (CC BY-NC-SA 4.0, non-commercial — fine while WebLens stays free) and Open Cookie Database (**Apache License 2.0** — corrected in v0.11.2, previously mislabeled CC0 in this doc) remain bundled as dated snapshots (currently 4,016 tracker domains; 2,251 cookie entries — 1,991 exact + 260 wildcard), with a refresh mechanism shipped opt-in in v0.11.0 and switched to **on by default** in v0.11.2 — see "v0.11.2" above.    **Broadening beyond Disconnect — researched, not decided or started.** In increasing order of real effort:
   - **DuckDuckGo Tracker Radar** — CC BY-NC-SA 4.0, same non-commercial restriction as Disconnect (DuckDuckGo requires contacting them for commercial use); would compound the existing NC constraint rather than diversify it. Exact current domain/entity count not published — would need a direct repo count before relying on a number.
   - **Ghostery TrackerDB** (successor to the old Cliqz/WhoTracks.me company data) — also CC BY-NC-SA 4.0, same restriction again.

Exact current rule count needs a direct pull to cite reliably; commonly described as tens of thousands of rules.
   - **WhoTracks.me data repo** (measurement/prevalence data, distinct from Ghostery TrackerDB) — content is CC BY 4.0, code MIT, also commercial-use-friendly, but its own public figures suggest meaningfully fewer tracked entities (~830) than Disconnect's 4,016, so it reads as a smaller, differently-scoped dataset rather than a straightforward superset.

Cost was never the real constraint; licensing is. If a paid tier is ever pursued (Open Decisions #8), only EasyList/EasyPrivacy and the WhoTracks.me data repo are unrestricted for that without a separate commercial license negotiation.

Adding `declarativeNetRequest` (M6) may increase Web Store review scrutiny — worth checking before submitting if that path is chosen. 4. **Build tooling.** Plain JS with no build step, or a bundler? Rule 1 favors no build step until something demands one.
5. **History size caps.** M5 introduces caps (oldest-evicted, 30 days/site, 200 sites) on the history store to bound `chrome.storage.local` growth. Exact numbers are an implementation default (documented in code comments), not re-litigated here, but should be revisited if real-world usage shows them too tight or too loose.
6. **"Verify and protect" feature set — resolved.** Of the original six-item proposal, cookie deletion and a separate restore flow were cut (restore is redundant with un-blocking, which is already a toggle); block-on-this-site, auto-reload-and-compare, a heavily-caveated breakage signal, and the before/after privacy receipt were built as M6. This was the project's first deliberate move from observe-only to a scoped, user-initiated intervention — see the M6 section above for the guardrails that keep it scoped.
7. **"What This Site Knows About You" — deferred, not resolved.** Proposed alongside Data Journey and the Data Exposure Detector; explicitly deferred by the user pending its own scope decision, since a full build would need a new `scripting` permission and content-script injection to observe device/behavior signals beyond what `webRequest`/`cookies` already expose — a new architecture surface, not an incremental addition to the existing one. The v0.12.0 User-Agent disclosure sentence (see "Data Exposure Detector" above) answers the "what does this know about my device" question truthfully without doing any of this — it states a standard HTTP fact, not a detection.
8. **Paid-tier ideas — discussed, not decided or scoped.** Raised as a brainstorm, not a commitment: (a) faster/broader list refresh, (b) extended history retention + locally-generated exportable reports, (c) the full "What This Site Knows About You" panel (see #7), (d) multi-device settings/history sync — the one idea here that actually requires new backend infrastructure, a real departure from "no backend, no server" and worth its own dedicated decision rather than a checkbox on a feature list, (e) team/organization deployment — a B2B angle, bigger scope than the others, data would need to stay on-device unless an admin explicitly opts into their own aggregation to avoid reopening the telemetry question the project has otherwise avoided.
